Kubernetes in Production

An architecture & design deep-dive for engineers running Kubernetes with paying customers on it. Optimised for people who already know what a Pod is and want to understand how the pieces fit together under load, on call, and during incidents.

How to read this

  1. Read Parts I–III linearly if you're new to internals. They form the mental model everything else depends on.
  2. Parts IV–X are reference. Jump to what you're building or breaking.
  3. Part XI is the field guide — pull it out during RFCs or design reviews.

Every section ends with production failure modes, a decision table, and links to primary sources.

Conventions

  • Commands assume kubectl ≥ v1.28 and a cluster with RBAC enabled.
  • "Production" means: paying customers on it, ≥ 99.9% SLO, on-call rotation attached.
  • "Should" is "do this unless you can articulate why not." "Must" is non-negotiable.

Part I

Foundations & Mental Models

Before you run anything in production, internalise what Kubernetes is, what it deliberately is not, and the contracts your workloads are signing up for.

1.1 What Kubernetes actually is

Kubernetes is a declarative, eventually-consistent cluster manager with:

  • A control plane that observes the cluster's actual state and reconciles it toward a desired state.
  • An API server as the single mutation surface — every read and write flows through it.
  • A scheduler that assigns workloads to nodes based on constraints and resources.
  • A set of controllers that each watch a slice of the API and drive state to match spec.
  • A CNI plugin that wires networking; a CSI plugin that wires storage; a CRI runtime that runs containers.

That's it. Everything else (Ingress, Service mesh, autoscaling, GitOps) is built on top of these primitives by you, by projects, or by your cloud provider.

The most important fact

The cluster is eventually consistent. There is no synchronous "deploy complete" event. There is only "spec submitted" and "spec observed" — and you choose how to interpret the gap.

1.2 What Kubernetes is not

It's NOTWhat you'll trip over
A deployment system for VMsPods are cattle, not pets. Long-running stateful services need extra plumbing.
A platformIt's a substrate. The platform (builds, releases, secrets, observability, policy) is what you build on top.
Self-healing for everythingIt restarts Pods. It does not retry in-flight requests, drain queues, or fix bad config.
A databaseetcd is a database, but your workloads don't get transactions across Pods and the API server.
Secure by defaultEKS/GKE/AKS apply some sane defaults. Self-managed clusters require explicit hardening.
A scheduler for batch jobs (out of the box)kube-scheduler schedules Pods. Job queues, cron, DAGs need Volcano, Argo Workflows, Kueue.

1.3 The three contracts you sign when you adopt it

  1. Pod lifecycle contract. Pods are mortal. IPs change. Disks attached via emptyDir vanish on restart. Files in the container's writable layer vanish with the container.
  2. Control plane as single point of mutation. You don't SSH to nodes and edit state. You don't write files to /etc/kubernetes/. You talk to the API server.
  3. Eventually consistent reconciliation. "3 replicas" means "the controller will keep working to make 3 replicas exist." Treat kubectl get as a snapshot, not a fact.

Every Pod gets an IP. Service objects give you a stable virtual IP that load-balances across a set of Pods selected by labels. The Pod IPs are real, routable across the cluster; Service IPs are virtual — they only exist because every node's data plane knows about them.

1.7 Production failure modes

  • Treating the cluster like a server (SSH, hand-edits, docker run). The control plane will eventually revert it, often silently.
  • Designing apps that need stable IPs or stable hostnames.
  • Assuming synchrony: kubectl apply returning is not the same as Pods running.
  • Mixing concerns in one Pod. A Pod is a unit of co-scheduling, not a VM.

Part II

Control Plane Internals

If Part I was about contracts, this part is about who's enforcing them.

2.1 Components

kube-apiserver

The front door. Every kubectl, every controller reconciliation, every kubelet heartbeat flows through it. Stateless and horizontally scalable. In production you run 2 or 3 instances behind a load balancer.

It is the chokepoint. Every pathological condition (slow controllers, runaway admission webhooks, debug loops calling the API) manifests here first.

etcd

Distributed KV store using Raft consensus. Holds the cluster state. The cluster's source of truth.

  • Slow disk = slow etcd = slow cluster. Use SSDs; ideally dedicated NVMe with low fsync latency.
  • Backing up etcd is backing up the cluster. etcdctl snapshot save cadence determines your RPO.
  • Writes go through Raft, so they cost network round-trips to a majority.
  • Default object size limit: 1.5 MiB. Push big data to object storage, not K8s objects.
Production rule

Never co-locate workloads on control-plane nodes (unless your distro mandates it and you understand the consequences).

kube-scheduler

Two phases: filtering (drop impossible nodes) and scoring (rank survivors). Scheduling is not retroactive — a Pod that becomes unschedulable after admission stays unschedulable until something changes.

kube-controller-manager

One binary that runs dozens of controllers in one process: ReplicaSet, Deployment, StatefulSet, Job, NodeLifecycle, ServiceAccount, Token, EndpointSlice, GarbageCollection, etc.

Each controller is an independent reconciliation loop:

for {
    desired := getSpec()
    actual := getStatus()
    if !reflect.DeepEqual(desired, actual) {
        patch := computePatch(desired, actual)
        client.Patch(patch)
    }
    sleep(someInterval)
    // OR: event-driven via informers + workqueue
}

2.2 The control loop pattern

Why this matters in production

Reconciliation loops can thrash. If your controller has a bug that flips a field back and forth, you'll see API server load climb without visible user action. Rate-limited retries on errors are not optional — a controller that calls the API in a tight loop during a transient outage will get itself throttled, then ignored.

2.3 The API server in detail

flowchart LR K[kubectl/client] --> A[kube-apiserver] A --> AU[Authentication
authn] A --> AM[Mutating admission] A --> AV[Validation
schema] AM --> AV AV --> VA[Validating admission] VA --> ET[etcd write] ET --> W[object available to watchers] style A fill:#d2a8ff22,stroke:#d2a8ff

Authentication

Order matters; first to claim an identity wins. Common: X.509 client certs, bearer tokens (SA JWTs / OIDC), webhook token authenticators.

Authorisation

After authn, every request is checked. RBAC is the default and the right answer. The authoriser chain: first to deny wins; if all allow, request proceeds. Be careful with Webhook authorsers that timeout — a slow policy decision is a security hole.

Admission control

  1. Mutating admission — runs first. May modify the object (Istio sidecar injector, cert-manager).
  2. Validating admission — runs second. May reject, may not modify (PodSecurity, ValidatingAdmissionWebhook).
Hard rules
  • Admission webhooks must be HA. If the webhook is down, all Pod creation hangs.
  • Webhooks must have a short timeout (set yours to 3s).
  • Never block on external IO in an admission webhook unless you can survive it being down.
  • failurePolicy: Fail is the safe default. Ignore is for emergencies only.

API server scaling

Bottlenecks: etcd write throughput (hard limit), watch cache memory (lots of controllers with broad watches = lots of RAM), network to etcd, admission latency (stacked webhooks).

Tuning flags: --max-requests-inflight (default 400/200), --max-mutating-requests-inflight (200), --request-timeout (60s — be careful), and --enable-priority-and-fairness — turn this on for production.

2.4 etcd deep-dive

Quorum and durability

3 nodes tolerates 1 failure. 5 nodes tolerates 2. More nodes ≠ more durable. Use an odd number. 3 nodes is the production sweet spot.

Storage layout

etcd writes ahead to WAL, then snapshots when WAL grows. etcdctl snapshot save /backup.db is your disaster recovery artefact. Cadence: every 15 minutes for typical clusters. Encrypt at rest. Test the restore quarterly.

Hard quota

--quota-backend-bytes default 8 GiB. When you hit this, etcd returns mvcc: database space exceeded. The cluster is dead. Monitor etcd_debugger_mvcc_db_total_size_in_bytes.

2.5 The scheduler in detail

Scheduling framework

PreFilter → Filter → PostFilter → PreScore → Score → NormaliseScore → Reserve → Permit → PreBind → Bind.

Plugins enabled by default: NodeResourcesFit, NodeAffinity, TaintToleration, PodTopologySpread, VolumeBinding.

2.6 High availability patterns

Control-plane HA

3 apiserver behind LB, 3 etcd members (co-located or separate), scheduler and controller-manager as 2 instances each with leader election.

Node failure

The kubelet stops heartbeating. The node-controller marks the node NotReady after threshold (default 40s). Then Pods are evicted (after --pod-eviction-timeout, default 5 minutes).

For stateful workloads: eviction is the right behavior for stateless. For databases, the application must handle losing a replica gracefully.

2.7 Production failure modes (Part II)

  • etcd running on spinning disks. Random write latency = random cluster-wide stalls.
  • Admission webhooks with no HA, slow responses, or tight timeouts.
  • API Priority and Fairness disabled.
  • Watches with broad selectors.
  • No etcd backups tested.
  • Co-locating etcd and workloads.
  • Skipping minor versions.
  • Single-instance scheduler/controller-manager with no leader election.

Part III

Networking

Networking is where Kubernetes stops feeling like a single machine. Most production outages have a network component; many begin there.

3.1 The four problems K8s networking must solve

  1. Container-to-container within a Pod — solved by sharing the Pod's network namespace.
  2. Pod-to-Pod across nodes — solved by the CNI plugin.
  3. Pod-to-Service — solved by kube-proxy programming iptables/IPVS.
  4. External-to-Service — solved by Ingress, LoadBalancer Service, or NodePort.

The Cluster Networking Contract: all Pods can communicate with all other Pods without NAT; all Nodes can communicate with all Pods without NAT; Pods see their own IP as the source.

3.2 CNI — Container Network Interface

CNIModelNotes
CalicoBGP or IP-in-IP, policyBattle-tested, strong NetworkPolicy, scales large
CiliumeBPFReplaces kube-proxy, identity-aware policy, observability built-in
AWS VPC CNIReal VPC IPs on PodsEKS default; uses ENIs, IP-hungry
Azure CNIReal VNet IPs on PodsAKS default
GKE Dataplane V2eBPF, Cilium-basedGKE default for newer clusters
FlannelSimple VXLAN overlayLightweight, dev-friendly, weak policy

Decision points

  • Overlay vs underlay. Overlay hides Pod IPs (easier IP planning, MTU/encap overhead). Underlay puts Pod IPs on the real network (better performance, observability, but you must plan IP space).
  • Policy enforcement. Calico and Cilium support full NetworkPolicy. Flannel is permissive.
  • eBPF vs iptables. eBPF (Cilium) scales better for large clusters with many Services.
  • Cloud-native integrations. AWS VPC CNI gets you security groups per Pod, ENI-level metrics.

IP address management

Allocate a Pod CIDR per node, non-overlapping with node network, Service CIDR, or anything routed in your VPC. Plan for 110–125% of current node count × max Pods per node.

MTU gotcha

VXLAN adds 50 bytes of overhead. If your underlying MTU is 1500, the overlay MTU must be 1450. Symptoms: large packets silently fail; monitoring works (small packets) but file transfers break.

3.3 Services in detail

TypeWhat it doesUse case

Session affinity and traffic policy

  • sessionAffinity: ClientIP — sticky to a Pod. Used for stateful protocols. Don't use it for HTTP.
  • externalTrafficPolicy: Cluster (default) — kube-proxy SNATs; original source IP is lost.
  • externalTrafficPolicy: Local — only sends to Pods on the receiving Node; preserves source IP. Drops traffic if no local Pod.

3.4 DNS — CoreDNS

  • Negative caching. Old NXDOMAIN answers stick for 5 seconds (default). A bad Service DNS that resolves once will keep failing for 5s.
  • Search path. Pods inherit <ns>.svc.cluster.local, svc.cluster.local, cluster.local.
  • DNS load. Every Service lookup goes to CoreDNS. Thousands of Services and short-lived connections = DNS bottleneck. Mitigations: NodeLocal DNSCache, caching in app, IP-based service discovery.

3.5 Ingress & Gateway API

ControllerNotes
ingress-nginxDefault in many distros; perf issues at scale
TraefikGood DX, middleware concept
HAProxy IngressSolid performance, less ergonomic
Envoy Gateway / IstioGateway API implementation, more powerful, more ops
Ingress → Gateway API

Ingress is deprecated in spirit. Gateway API is the successor: more expressive, multi-protocol, role-oriented. If you're starting a new cluster, plan to use Gateway API.

3.6 NetworkPolicy

NetworkPolicy is the Kubernetes firewall. Pod-to-pod, namespace-to-namespace. No policy = all traffic allowed.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}
  policyTypes: ["Ingress"]

3.7 Service mesh

A mesh puts a sidecar proxy in every Pod. Handles mTLS, L7 routing, retries, circuit breaking, telemetry, authz policy.

Production trade-offs
  • Cost: sidecars consume memory and CPU. 1000 Pods × 100 MiB = 100 GB. Mitigations: eBPF mesh (Cilium, Linkerd), Istio Ambient.
  • Latency: sidecar adds a hop. p99 goes up a few ms.
  • Operational complexity: mesh upgrades, control plane HA, debug story.

Recommendation: start without a mesh. Add one when you have a concrete need (mTLS at scale, L7 routing across many services).

3.8 Production failure modes (Part III)

  • CNI MTU mismatch.
  • ClusterIP exhaustion.
  • DNS as the bottleneck.
  • NetworkPolicy that blocks DNS.
  • kube-proxy iptables scaling.
  • ExternalTrafficPolicy mishandling.
  • Cloud L4 LB idle timeout longer than app keepalive.
  • No source NAT policy.

Part IV

Workloads & Scaling

The objects that actually run your code. Where most operational decisions live.

4.1 Deployments and the rolling update contract

A Deployment manages a ReplicaSet, which manages Pods. Rolling updates replace ReplicaSets in waves:

flowchart LR A["v1
Replicaset A (5 replicas)"] -->|"scale down 1"| B["v1 → v2
A:4, B:1"] B --> C["A:3, B:2"] C --> D["A:2, B:3"] D --> E["A:1, B:4"] E --> F["A:0, B:5
v2 deployed"] style A fill:#3fb95022,stroke:#3fb950 style F fill:#1f6feb22,stroke:#58a6ff 
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
Production rule

Set maxSurge and maxUnavailable explicitly. Don't rely on defaults (25%/25%).

Health checks: the contract for "ready"

spec:
  containers:
    - name: app
      livenessProbe:
        httpGet: { path: /healthz, port: 8080 }
        initialDelaySeconds: 10
        periodSeconds: 10
        failureThreshold: 3
      readinessProbe:
        httpGet: { path: /ready, port: 8080 }
        periodSeconds: 5
        failureThreshold: 2
      startupProbe:
        httpGet: { path: /healthz, port: 8080 }
        failureThreshold: 30
        periodSeconds: 5
Liveness ≠ readiness

Liveness restarts the container; readiness just stops traffic. If liveness fails during a transient backend outage, every Pod restarts in sync — thundering herd.

PodDisruptionBudget (PDB)

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: api
If you don't set a PDB

The cluster will happily drain every Pod of your service at once. This is one of the most common production outages from "innocent" node maintenance.

4.2 Resource management

QoSWhenBehavior on node pressure
Guaranteedrequests == limits for CPU and memoryLast to be killed
Burstablerequests set, limits > requests or one missingKilled after BestEffort
BestEffortNo requests or limitsKilled first
BestEffort is dangerous in production

A noisy-neighbor Pod can be killed to free memory for a Guaranteed Pod. Don't run production workloads BestEffort.

CPU vs memory behavior

  • CPU is compressible. A limit caps the rate but doesn't OOM-kill.
  • Memory is incompressible. Hit the limit → kernel OOM-killer fires → Pod restarts.
  • Memory limits need headroom for heap, GC, page cache. Profile your app.

4.3 Horizontal Pod Autoscaler (HPA)

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 3
  maxReplicas: 50
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
  • HPA needs a metrics pipeline (metrics-server for CPU/memory; Prometheus Adapter for custom).
  • HPA doesn't scale from zero by default. Use KEDA for that.
  • Don't autoscale on raw CPU alone. Pair with custom business metric.
  • Set min > 1 for prod services. A single Pod with a node failure = zero replicas.
  • HPA decision latency is 15s default.

4.4 Vertical Pod Autoscaler (VPA)

  • Modes: Off (recommendations), Initial (set on Pod creation), Auto (live-update, evicts Pods).
  • VPA in Auto mode conflicts with HPA on CPU/memory. Pick one.
  • Production usage: run VPA in Off mode as a recommendation engine.

4.6 StatefulSets

Stable, ordered network IDs. Stable, per-Pod storage. Ordered rolling updates. Use for databases, queues, Zookeeper, etcd, Consul — anything that can't tolerate peer swapping.

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db
  replicas: 3
  selector:
    matchLabels:
      app: db
Production gotchas
  • Ordered scaling is slow.
  • No auto-rebalancing across nodes.
  • Default update strategy is OrderedReady.

For real databases, use a dedicated operator (CloudNativePG, Zalando, MongoDB Operator, Strimzi for Kafka).

4.7 DaemonSets

One Pod per node. Used for logging agents, node metrics exporters, CNI components, storage daemons.

Production rule

Tolerations are critical. Without them, your logging agent won't run on tainted nodes (and you'll have a blind spot exactly where you need logs).

4.8 Jobs and CronJobs

  • Set ttlSecondsAfterFinished — Job objects accumulate and clutter the API.
  • Set activeDeadlineSeconds — stuck Jobs otherwise live forever.
  • CronJob concurrencyPolicy: Forbid unless you specifically want overlap.
  • For complex DAGs, use Argo Workflows or Dagster.

4.9 Init containers and sidecars

  • Init containers run before main; used for migrations, waiting for deps, fetching config.
  • Sidecars (native, 1.28+) share the Pod lifecycle with the main container.
  • Sidecars that fail can kill the Pod — set restart policy on them.

4.10 Priority classes and preemption

kind: PriorityClass

  name: production-critical

4.11 Production failure modes (Part IV)

  • No PDB set.
  • Liveness probe too aggressive.
  • Memory limits too tight.
  • HPA on CPU only.
  • CA/Karpenter misconfigured.
  • StatefulSet without an operator.
  • CronJob without concurrencyPolicy: Forbid.
  • No startup probe on slow apps.
  • No priority class.

5.3 PVCs

RWO is the common case. RWX is expensive (NFS or object-backed). RWOP is the new ideal for databases (no two Pods ever mount the same volume).

5.4 StorageClass and dynamic provisioning

  name: gp3

  type: gp3
  iops: "3000"

  encrypted: "true"

volumeBindingMode

WaitForFirstConsumer is the production default — PV is created when Pod is scheduled, in the same AZ. Immediate can create a PV in the wrong AZ.

5.7 Production gotchas

  • The "local" storage trap — Local volumes (hostPath, local PV) are tied to a node. If the node dies, the data is gone.
  • The "PV stuck in Terminating" problem — Force-remove the finalizer: kubectl patch pv <name> -p '{"metadata":{"finalizers":null}}'
  • "I deleted the StatefulSet but kept the PVCs, now I'm restoring from old data" surprise — PVCs are not deleted with StatefulSets by default.
  • Snapshot/backup retention — Most cloud providers charge per GB. Implement retention policies.

5.9 Production failure modes (Part V)

  • volumeBindingMode: Immediate in StorageClass.
  • EBS volume in wrong AZ.
  • Snapshot without retention policy.
  • emptyDir for data you need.
  • hostPath in production.
  • No expansion policy.
  • PVCs left in Released.
  • Local PVs without replication.
  • CSI driver crash-looping.

Part VI

Security

Production security is layered: identity, isolation, supply chain, runtime.

6.1 The threat model

  1. Compromised Pod — attacker has RCE in your container. Goal: prevent lateral movement, data theft, persistence.
  2. Compromised credentials — leaked SA token, stolen kubeconfig.
  3. Compromised supply chain — malicious image, malicious dependency.
  4. Compromised node — attacker has root on a node.
  5. Compromised operator — malicious or careless human with cluster admin.
  6. Compromised cloud account — IAM credentials for the cluster.

6.2 Pod Security Standards (PSS)

LevelWhat it allowsUse
PrivilegedAnythingSystem/infra Pods only
BaselineBlocks most escalationsDefault for non-prod
RestrictedHardened best practiceDefault for production
 
apiVersion: v1
kind: Namespace
metadata:
  name: prod
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted

What restricted enforces

  • runAsNonRoot: true
  • seccompProfile.type: RuntimeDefault
  • allowPrivilegeEscalation: false
  • capabilities.drop: [ALL]
  • readOnlyRootFilesystem: true (best practice)

6.3 RBAC

Production RBAC patterns
  • Service accounts per workload. Not one SA per namespace; one SA per app, scoped tight.
  • Don't use the default SA.
  • Humans get cluster-scoped roles sparingly.
  • Aggregation with aggregationRule.clusterRoleSelectors.

6.4 ServiceAccounts and tokens

Pre-1.24: every SA got a long-lived bearer token, auto-mounted. 1.24+: tokens are bound to the lifetime of the Pod via projected tokens. Set automountServiceAccountToken: false on Pods that don't need API access.

Audience-scoped tokens are used for IRSA (AWS), GKE Workload Identity, Azure Workload Identity.

6.5 Secrets management

Kubernetes Secrets are base64-encoded, not encrypted by default. Real secret management uses one of:

  1. Encrypt at rest in etcd (EncryptionConfiguration). All major providers do this by default.
  2. External secret stores. Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault.
  3. Sealed Secrets (Bitnami), External Secrets Operator (syncing from cloud stores).
  4. Direct CSI driver for Vault (secrets-store.csi.k8s.io).
Don't put secrets in env vars

Env vars leak to: kubectl describe pod output (visible to anyone with read), crash dumps, child process arguments, logs that include os.Environ().

6.7 Image supply chain

  • Private registries — ECR, GCR, ACR, Harbor, Quay.
  • Build-time scanning — Trivy, Grype, Snyk in CI.
  • Admission-time — Kyverno, OPA/Gatekeeper, Connaisseur.
  • Signing — Sigstore/Cosign. Verify at admission.
  • SLSA levels — Aim for at least Level 2 for production images.
apiVersion: kyverno.io/v1

6.8 Runtime security

  • AppArmor / SELinux / seccomp — kernel-level confinement.
  • gVisor, Kata Containers — user-space kernel; isolate syscalls. Performance trade-off.
  • Falco — runtime threat detection. Watches syscalls, k8s audit, network.
  • Tracee — eBPF-based alternative to Falco.

6.11 Production failure modes (Part VI)

  • Default SA in use.
  • SA token auto-mounted on Pods that don't need it.
  • NetworkPolicy not enforced (Flannel).
  • Secrets as env vars.
  • Privileged containers in production.
  • No image scanning.
  • No admission control.
  • Cluster-admin to many humans.
  • Audit logs disabled.

Part VII

GitOps & Continuous Delivery

GitOps is the operational model that fits Kubernetes best. The cluster reconciles toward Git; humans push commits; the system does the rest.

7.1 What GitOps actually is

  1. Declarative configuration (YAML, Helm, Kustomize) describes the desired cluster state.
  2. Versioned in Git as the single source of truth.
  3. Automatically applied by an agent that watches Git (or repo) and reconciles the cluster.
  4. Audited via Git history: who changed what, when, and why.

7.8 Drift detection

The reconciler compares cluster state to Git. If they differ (someone ran kubectl edit, an autoscaler changed something), it's drift.

  • Self-heal in Argo / prune: true in Flux: the agent reverts the cluster to Git state.
  • Disable self-heal for stateful workloads where the agent shouldn't revert legitimate changes.

7.9 Secrets in GitOps

Options: External Secrets Operator, Sealed Secrets, SOPS, Vault Agent Injector. Pick based on rotation cadence, compliance, tooling tolerance.

7.11 Production failure modes (Part VII)

  • Git is not the source of truth. Self-heal hides it; revert shows up later.
  • Argo CD without HA. Central server is a SPOF.
  • Helm chart overrides everywhere.
  • Sync windows not configured. Auto-sync during an incident can clobber mitigations.
  • Manifest sprawl.
  • No drift detection policy.
  • Long-lived branches.

You can't operate what you can't see. Kubernetes observability has four pillars and many pitfalls.

The golden signals

For each service: Rate, Errors, Duration, Saturation.

8.2 Metrics — Prometheus and the ecosystem

What to scrape

Production Prometheus rules

  • Retention: 30 days local, longer in object storage. Cardinality is the cost driver.
  • Cardinality: http_requests_total with path and user_id labels is a footgun.
  • Sharding: at scale, split Prometheus into multiple shards.
  • Recording rules: precompute expensive queries.

8.3 Logs

Log patterns

  • Node-level: kubelet writes to /var/log/containers/ or /var/log/pods/.
  • Sidecar pattern: sidecar tails stdout, forwards to log store. Heavy at scale.
  • Node-level agent: DaemonSet (Fluent Bit, Vector, Filebeat). Production default.
  • Cloud integration: GKE → Cloud Logging; EKS → CloudWatch; AKS → Log Analytics.
Structured logging

Production logs must be JSON. Stdout from app.log("user signed in") is unactionable. Stdout from app.log({event: "user_signed_in", user_id: 123}) is searchable, aggregatable, alertable.

8.4 Traces

Distributed tracing correlates a request across services. OpenTelemetry is the standard.

flowchart LR A["service A
OTel SDK"] --> C["OTel Collector"] B["service B
OTel SDK"] --> C E["service C
OTel SDK"] --> C C --> T[Tempo / Jaeger] style C fill:#1f6feb22,stroke:#58a6ff

Sampling

  • Head-based — decides at request start. Easy, predictable.
  • Tail-based — decides after the request, based on outcome. Catches rare errors. Harder to scale.
  • Start at 1-10%; 100% on error paths.

8.5 Events and Kubernetes-aware signals

  • EventRouter — ships Events to a log store.
  • kube-state-metrics — K8s state to Prometheus metrics.

Useful alerts: Pod CrashLoopBackOff > 5 min, FailedScheduling, Node NotReady > 5 min, image pull errors.

8.6 The four signals together — what "good" looks like

A production service has metrics, logs, traces, and events. The signals must be correlated. Click a metric spike → see the traces → see the logs → see the events. This is the difference between 10-minute MTTR and 4-hour MTTR.

8.8 Production failure modes (Part VIII)

  • Cardinality explosion.
  • Logging without trace context.
  • Alerts on every metric. Alert fatigue → real alerts ignored.
  • Logs in the container filesystem.
  • No SLO definition.
  • Health checks failing logged at ERROR.
  • No event capture.
  • Sampling 0% in production.
  • Sampling 100% in production. Bill of $200k/month.

Part IX

Reliability & Day-2 Operations

The part that determines whether your on-call is survivable.

9.1 Upgrades

Cluster upgrades

Production upgrade cadence: every 3-6 months. Lateness compounds (you can't skip minors).

Pre-upgrade checklist:

  1. Read release notes for every minor between current and target.
  2. Run pluto and kubectl-versions to find deprecated APIs.
  3. Read CNI, ingress, and operator upgrade notes.
  4. Upgrade control plane first.
  5. Upgrade node pools / node groups one at a time.
  6. Verify after each step.

9.2 Backups and disaster recovery

What you back up

ComponentWhyTool
etcdSource of truth for cluster stateetcdctl snapshot
Persistent volumesApplication dataCSI snapshots, Velero
Git reposConfig, manifestsGitHub/GitLab backup
SecretsEncrypted secretsVault backup, cloud KMS

Velero

The de facto K8s backup tool. Backs up cluster resources + PV snapshots. Schedule daily; retain 7 daily + 4 weekly + 12 monthly. Test restores quarterly.

etcd backups

Production rules
  • Snapshot every 15 minutes to object storage.
  • Encrypt backups (KMS).
  • Test restore in a sandboxed cluster quarterly.
  • Document the restore procedure as a runbook.

9.3 Capacity planning

What to measure

  • CPU and memory usage at node level (cluster utilisation ~70% before scaling).
  • Pod count vs node capacity.
  • Storage usage trends.
  • Network bandwidth.

Most prod clusters should run at ~65-75% cluster CPU, ~70% memory, with 5-10% node headroom.

Production chaos rules

  1. Start in non-prod.
  2. Start small.
  3. Have a blast radius cap.
  4. Stop conditions.
  5. Hypothesis-driven.
  6. Game days.

9.5 Incident response

Runbooks

Every alert needs a runbook. The runbook should: link from the alert; tell you what to check first; tell you what to do; tell you when to escalate.

Postmortems

Blameless. Focus on timeline (facts), root cause (not "human error" — that's a process gap), contributing factors, action items.

  • PDB unset.
  • No game days.
  • Blameless postmortems, blameful culture.

Part X

Multi-Cluster & Federation

Most production setups eventually need more than one cluster. The question is why, and what pattern fits.

10.1 Why multiple clusters?

ReasonExamples
Region/zone isolationReduce blast radius; data residency
ComplianceGDPR data stays in EU; FedRAMP workloads segregated
Separation of concernsProd vs staging; per-team clusters
CostDifferent node types, spot vs on-demand
Burst capacityPrimary region + overflow
Caveat

If your reason is "HA," a single multi-AZ cluster usually suffices. Multiple clusters add operational cost; have a real reason.

10.3 Patterns

Pattern 1: Independent clusters, same Git

Each cluster has its own Argo/Flux installation. Git repo has per-cluster directories.

Pattern 2: Cluster API (CAPI)

A Cluster CRD, a control-plane KubeadmControlPlane, a MachineDeployment. The management cluster creates and reconciles workload clusters.

Pattern 3: Hub-and-spoke with Submariner or Skupper

Multiple clusters that need network connectivity at the application layer. Submariner (L3) and Skupper (L7) provide cross-cluster Pod-to-Pod networking.

Pattern 4: Multi-cluster service mesh

Istio and Linkerd can span multiple clusters as one mesh. Enables cross-cluster failover, geographic traffic routing, shared identity.

11.2 The RFC checklist

Architecture

  • What does the cluster topology look like? Multi-AZ? Multi-region?
  • Does this fit existing patterns (Deployment + HPA + PDB + Service + Ingress)?
  • Does this need a CRD / Operator?
  • How does this interact with the CNI policy and NetworkPolicies?

Workload

  • Is it stateless? If stateful, what's the storage strategy?
  • What are the resource requests and limits, and how were they chosen?
  • Are health checks (startup, readiness, liveness) defined correctly?
  • Is there a PDB? Are maxSurge/maxUnavailable set?
  • What's the rollout strategy? Can we roll back?

Scaling

  • What metric drives scaling? CPU, custom, queue depth?
  • What's the minimum replica count? Enough to survive one node failure?
  • Does this interact with the cluster autoscaler / Karpenter?
  • Is there a scale-down stabilisation window?

Security

  • What Pod Security Standard level? restricted?
  • What ServiceAccount? Specific or default?
  • Are Secrets mounted as files or env vars? Where do they come from?
  • Are images signed? Scanned?
  • Does the workload need privileged? Can it be avoided?
  • What NetworkPolicies apply? Egress allowed?

Observability

  • What are the SLIs (rate, errors, duration, saturation)?
  • Are alerts defined? Runbook linked?
  • Are logs structured? Trace context propagated?
  • What dashboards will this show up on?

Reliability

  • What's the SLO target?
  • What's the rollback plan?
  • What's the failure mode?
  • Has chaos testing been done? Game day planned?
  • Are dependencies monitored? What if the DB is slow?

Cost

  • What node type does this run on?
  • Right-sized or oversized? VPA recommendations?
  • Spot-eligible?
  • What's the per-month cost?

Day-2

  • Upgrade path documented?
  • Backup covered? Tested?
  • Runbook for common failures?
  • Who owns this on-call?

11.6 The questions to ask before every production decision

For a new service

  1. What's its SLO? (Don't answer "high availability" — give me a number.)
  2. What's its blast radius? (How many users are affected if it's down?)
  3. What's its failure mode? (What happens when this dies?)
  4. Who owns it on-call?

For a new dependency

  1. What does it cost if it's slow?
  2. What does it cost if it's wrong?
  3. How do we know it's broken before users do?

For an architectural change

  1. What's the rollback story?
  2. What's the failure mode? (Worst case?)
  3. Have we tested the failure mode?
  4. Does this need a game day?

For an incident

  1. What's the user impact right now?
  2. What's the smallest mitigation?
  3. Can we rollback?
  4. What's the trigger?

For a cost decision

  1. What's the per-month cost? Per-year? Per-user? Per-request?
  2. Is this an optimisation or a tax?
  3. Who pays? Who benefits?

11.7 The "production-ready" checklist

A service is production-ready when:

  • Deployed via GitOps.
  • Has resource requests and limits set.
  • Has PDB.
  • Has priority class.
  • Has startup, readiness, liveness probes.
  • Logs are structured JSON with trace_id.
  • Exposes Prometheus metrics (RED + saturation).
  • Alerts tied to SLO burn.
  • Runbook exists.
  • Image scanned and signed.
  • ServiceAccount scoped.
  • NetworkPolicy in place.
  • Secrets from external store (Vault, cloud KMS).
  • Health checked at least weekly (synthetic).
  • Owner and on-call rotation defined.
  • Capacity forecast exists.

11.8 Closing

Kubernetes is a substrate, not a product. It gives you a powerful set of primitives and an operational model. Whether it works for you depends entirely on what you build on top.

The architecture and design decisions in this reference aren't the only path. They're the path that survived production. When you deviate, document why; the next engineer on the team needs to know.

When something goes wrong — and it will — the answer is rarely "more Kubernetes." It's usually "fewer things, tested, observable, with humans who know what to do."
